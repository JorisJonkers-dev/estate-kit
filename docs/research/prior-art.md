## Takeaways for estate-kit

1. **Pull the artifact, coordinate the switch.** NixOS tooling splits into push tools (NixOps, colmena, deploy-rs, morph, krops, nixinate, clan) and pull agents (comin, bento, Cachix Deploy, `system.autoUpgrade`). Burgess's convergent agents and the Delaet survey favour pull for robustness and scale. But no pull agent here coordinates across nodes; the push tools coordinate but cannot survive their own target. The pattern that works is Cachix Deploy's: nodes pull a signed, pinned closure, and a central actor decides *when* each node may activate.
2. **Split the rollout into a harmless phase and a disruptive phase.** van der Burg's atomic upgrading copies every closure to every node first, which needs no coordination. Only then does it switch, in a short window. The Nix store makes the first phase free and a rollback a pointer flip, so the applier only has to serialise the activate-or-reboot step.
3. **Drain is done by a cluster-side controller holding a lock, not by the host and not by an external pusher.** kured and system-upgrade-controller both take a cluster-wide lock, cordon, and evict through the Eviction API so PodDisruptionBudgets hold. Only then do they let the node act. Borg treats maintenance as a rate-limited eviction cause, and Twine goes further: applications can approve or delay host maintenance. estate-kit should express drain the same way (PDB-respecting eviction, one lock), never as a `kubectl drain` over SSH.
4. **"One node updates another" already exists as the DaemonSet-plus-lock pattern.** The worker runs on the node it changes, the decision and lock live in the API server, and any node can resume after the lock holder dies. A literal node-A-pushes-to-node-B design reinvents this with worse failure modes, for example when A is next in line.
5. **A maintenance window gates when work starts, not when it ends.** That is how kured and SUC define it (SUC's `window` reuses kured's code). Keep "switch without reboot" separate from "reboot required" (kernel, initrd, systemd). The window should gate only the reboot, and the need to reboot can be derived by comparing the booted and current system generations.
6. **No mutable central store of desired state.** Charon/NixOps's state database was its weakest point, and colmena and deploy-rs dropped it. Borg, Omega and Kubernetes, Facebook's Configerator and GitOps all keep desired state in versioned, reviewable sources, signed if possible (in-toto, Flux Cosign). Hold desired state in Git or OCI renders. Keep only *observed* state and locks in the cluster API (node annotations, Leases), where they can be rebuilt from the world.
7. **Separate controllers, one model.** The Omega and Kubernetes lesson is many small level-triggered controllers sharing one store, not a monolithic orchestrator. kured, SUC and Flux are separate, and they coordinate only through API objects (cordon, taints, PDBs). Let one compiler render both the cluster tree and the per-node Nix configs. Deliver them through separate controllers: Flux for workloads, a node-rollout controller for hosts.
8. **Make the host applier a provably convergent reconciler.** Sieve and Anvil find controller bugs in exactly this shape: a crash between drain and uncordon, stale views, a node stuck cordoned. Persist each node's step and target generation as observed state. Make every step idempotent, aim for eventual stable reconciliation, and test with injected crashes.
9. **Roll hosts like Flagger rolls pods.** Start with one canary node, then batches. Gate on health: node Ready, evicted pods rescheduled and Ready, SLO metrics compared with untouched nodes (Davidovič and Beyer, Kayenta). Roll back automatically by booting the previous generation, with deploy-rs's magic rollback as the per-node safety net.
10. **Test the mixed-version state, not just the end state.** Zhang et al. find most rolling-upgrade failures come from old and new versions coexisting, and Dumitraş finds procedural errors dominate. The k3s server/agent version-skew rule and stateful workloads (schema changes, de Jong et al.) belong in the model as rollout constraints.
11. **The host model has well-studied shapes.** EDMM and TOSCA reduce deployment to components, relations and lifecycle operations. Disnix splits services, infrastructure and distribution models. Models@runtime and van der Burg's self-adaptive framework feed discovered facts (hardware, disks via disko) back into the model. Reuse these splits rather than inventing a new device schema.
12. **Dry-run hosts the way renders are dry-run.** NixOS VM tests, from van der Burg's declarative-VM work, can boot each generated node config before any node applies it. They are the host counterpart of the render dry-run, and the negative-fixture discipline Rahman et al. find missing in IaC research.
