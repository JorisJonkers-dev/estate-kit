# One cluster or several, and many Tenants in one

Research note, 2026-11-01. It gathers what primary sources say about growing from one Kubernetes cluster to several, delivering to several with Flux, connecting them, and keeping more than a thousand Tenants apart inside one. It is research, not a decision: [record 1](../decisions/0001-one-maintainer-one-cluster-one-estate.md) still holds the estate to one cluster. Sections 1 to 4 report sources; section 5 is interpretation and says so.

Two futures frame it. In (A), several estates each run their own estate-kit service and interoperate. In (B), one large cluster serves many Tenants, with development, staging and production side by side.

## 1. One large cluster or several

### What upstream says one cluster can hold

Kubernetes v1.37 is designed for clusters of at most 5,000 nodes, 110 pods per node, 150,000 pods and 300,000 containers, all at once ([Considerations for large clusters](https://kubernetes.io/docs/setup/best-practices/cluster-large/)). The same page suggests moving Event objects to a dedicated etcd instance to help large clusters.

SIG Scalability's thresholds add per-object limits: 10,000 namespaces, 3,000 pods per namespace, 10,000 Services per cluster, 5,000 Services per namespace, and 150,000 objects per (non-Event) resource type ([thresholds](https://github.com/kubernetes/community/blob/master/sig-scalability/configs-and-limits/thresholds.md)). They are not hard limits: crossing one degrades performance rather than failing the cluster, and a smaller cluster has proportionally lower limits (same source).

etcd caps a request at 1.5 MiB and storage at 2 GiB by default, configurable up to a suggested maximum of 8 GiB ([etcd limits](https://etcd.io/docs/v3.5/dev-guide/limit/)).

Vendors plan well below the upstream ceiling. AWS says to plan how a cluster will grow beyond 300 nodes or 5,000 pods, and notes that one large cluster reduces operational load but has trade-offs for multi-region deployment, tenant isolation and cluster upgrades ([EKS scalability](https://docs.aws.amazon.com/eks/latest/best-practices/scalability.html)).

### k3s specifically

k3s sizes a single server by agent count: 2 CPU and 4 GB for up to 350 agents, 4 CPU and 8 GB for up to 900, 8 CPU and 16 GB for up to 1,800; an HA control plane carries roughly 50% more. It says to join agents in batches of 50 or fewer, and to change the default `cluster-cidr` to go beyond 255 nodes ([k3s requirements](https://docs.k3s.io/installation/requirements)).

k3s has three datastores. Embedded SQLite is the default and "cannot be used on clusters with multiple servers"; embedded etcd supports several servers; an external etcd, MySQL, MariaDB or PostgreSQL is reached through `datastore-endpoint` ([k3s datastore](https://docs.k3s.io/datastore)). The SQL backends go through kine, an etcd shim that implements only the subset of the etcd v3 API the API server needs ([kine](https://github.com/k3s-io/kine)). For production and large clusters k3s recommends HA with an external database ([k3s requirements](https://docs.k3s.io/installation/requirements)). Network flags such as `--cluster-cidr` must match on every server ([k3s HA embedded etcd](https://docs.k3s.io/datastore/ha-embedded)).

### Why operators split anyway

The limits are rarely what splits a cluster. AWS calls Kubernetes "a single tenant orchestrator" and the cluster "the only construct that provides a strong security boundary", because a host escape exposes every Secret and volume on that node and lets the attacker impersonate its kubelet ([EKS tenant isolation](https://docs.aws.amazon.com/eks/latest/best-practices/tenant-isolation.html)). Zalando ran 100+ clusters, each in its own AWS account, citing weak multi-tenancy, a limited blast radius, cost attribution and the cluster as an access boundary; one cluster hit its pod-CIDR allocation at 250 nodes ([Henning Jacobs, Zalando](https://srcco.de/posts/many-kubernetes-clusters.html)).

Upgrades are the other reason. An in-place upgrade moves one minor version at a time, and several sequential upgrades carry more risk of downtime; a blue/green cluster upgrade can switch back, but needs two clusters in parallel, a new API endpoint for consumers, and care with stateful workloads ([EKS cluster upgrades](https://docs.aws.amazon.com/eks/latest/best-practices/cluster-upgrades.html)).

Splitting has its own price. A cluster per tenant is expensive, fragments capacity, needs fleet tooling, and is slow to create compared with a namespace ([EKS tenant isolation](https://docs.aws.amazon.com/eks/latest/best-practices/tenant-isolation.html)). Kubernetes' own guidance: "The benefit of stronger tenant isolation must be evaluated against the cost and complexity of managing multiple clusters" ([multi-tenancy](https://kubernetes.io/docs/concepts/security/multi-tenancy/)).

## 2. Delivering to several clusters with GitOps

### Flux per cluster, or a hub

Flux runs in one of two shapes. In standalone mode every cluster runs its own controllers; in hub-and-spoke a central cluster's controllers reconcile spoke clusters through their API servers ([Flux architecture overview](https://control-plane.io/posts/fluxcd-architecture-overview/)). Standalone gives a smaller attack surface (no API server is exposed), a smaller blast radius, and suits hard multi-tenancy and air-gapped clusters, at the cost of bootstrapping, upgrading and monitoring each instance separately. A hub is bootstrapped once and gives one view, but it is a single point of failure for delivery, a compromised hub reaches every spoke, and the hub must reach every spoke's API server (same source). The mechanism is a Kustomization's `spec.kubeConfig`, which reconciles it entirely on a remote cluster ([Flux Kustomization](https://fluxcd.io/flux/components/kustomize/kustomizations/)). A hub needs horizontal scaling and can be sharded across Flux instances ([Flux architecture guide](https://fluxcd.control-plane.io/guides/flux-architecture/)); sharding by the `sharding.fluxcd.io/key` label is Flux's documented path for "tens of thousands of applications" ([Flux sharding](https://fluxcd.io/flux/installation/configuration/sharding/)).

Open Cluster Management is a pull-based hub. The hub stores each cluster's desired state and "won't directly request against the real clusters"; an agent on each cluster pulls, so a managed cluster needs only to reach the hub, keeps running if the hub is down, and the hub can manage thousands of clusters ([OCM architecture](https://open-cluster-management.io/docs/concepts/architecture/)). Karmada, a CNCF incubating project, propagates resources to member clusters by PropagationPolicy ([Karmada](https://karmada.io/docs/), [architecture](https://karmada.io/docs/core-concepts/architecture)). Liqo peers clusters and shows a remote cluster as one virtual node, offloading namespaces onto it ([Liqo](https://docs.liqo.io/en/stable/)). KubeFed was archived on 2023-01-03 ([SIG-Multicluster](https://multicluster.sigs.k8s.io/)).

### A fleet inventory

KEP-4322 defines ClusterProfile (`multicluster.x-k8s.io/v1alpha1`), a namespaced object per member cluster; the profiles in one namespace form one cluster inventory, and each is written by exactly one cluster manager. Its status holds the Kubernetes version, name/value properties, conditions such as `ControlPlaneHealthy` and `Joined`, and access providers that say how to reach and authenticate to the cluster but must hold no secret. It leaves orchestration and a reference implementation out of scope ([KEP-4322](https://github.com/kubernetes/enhancements/blob/master/keps/sig-multicluster/4322-cluster-inventory/README.md)). Cluster managers that publish it include OCM, KubeFleet and GKE Fleet (preview); consumers include Kueue, Headlamp and an Argo CD labs integration. Flux is not listed ([implementations](https://multicluster.sigs.k8s.io/implementations/cluster-inventory-api-implementations/)).

KEP-2149's ClusterProperty names a cluster: `cluster.clusterset.k8s.io` holds an ID that must be an RFC 1123 DNS subdomain under 128 characters, unique within its ClusterSet for the whole membership, and `clusterset.k8s.io` names the set. It recommends the `kube-system` namespace UID as a stable ID ([KEP-2149](https://github.com/kubernetes/enhancements/blob/master/keps/sig-multicluster/2149-clusterid/README.md)).

OCM separates choosing from deploying: Placement selects clusters by label and writes a PlacementDecision, a list of cluster names that other controllers act on ([OCM architecture](https://open-cluster-management.io/docs/concepts/architecture/)).

### Cells: placing Tenants on clusters

AWS defines a cell as a complete, independent instance of a workload that shares no state with other cells, a thin cell router that sends each request by partition key, and a control plane that provisions cells and migrates customers between them ([what is a cell](https://docs.aws.amazon.com/wellarchitected/latest/reducing-scope-of-impact-with-cell-based-architecture/what-is-a-cell-based-architecture.html)). The partition key must match the service's grain, such as a customer ID, and needs a plan for a customer too large for one cell; cross-cell calls should go back through the router rather than cell to cell ([cell partition](https://docs.aws.amazon.com/wellarchitected/latest/reducing-scope-of-impact-with-cell-based-architecture/cell-partition.html)). The router should hold as little business logic as possible and keep serving other cells when one is unreachable ([cell routing](https://docs.aws.amazon.com/wellarchitected/latest/reducing-scope-of-impact-with-cell-based-architecture/cell-routing.html)). Cells should have a capped, consistent maximum size, small enough to test at full scale ([cell sizing](https://docs.aws.amazon.com/wellarchitected/latest/reducing-scope-of-impact-with-cell-based-architecture/cell-sizing.html)), and changes roll out in waves, cell by cell ([cell deployment](https://docs.aws.amazon.com/wellarchitected/latest/reducing-scope-of-impact-with-cell-based-architecture/cell-deployment.html)). AWS lists the costs plainly: more complex architecture, higher infrastructure cost, specialised tooling, and a routing layer to build; and it asks whether it is better "for 100% of customers to experience a 5% failure rate, or 5% of customers to experience a 100% failure rate" ([when to use](https://docs.aws.amazon.com/wellarchitected/latest/reducing-scope-of-impact-with-cell-based-architecture/when-to-use-a-cell-based-architecture.html)).

Two engineering accounts show the pattern in practice. Slack made each availability zone a cell: services talk only within their zone, and operators drain a bad zone by setting its weight to zero at the edge Envoy, which finishes in-flight requests ([Slack](https://slack.engineering/slacks-migration-to-a-cellular-architecture/)). Shopify's pod is a set of shops on fully isolated datastores; a router in the load balancer tags each request with its pod, no action reaches across pods, and a whole pod moves to its recovery data centre in about a minute ([Shopify](https://shopify.engineering/a-pods-architecture-to-allow-shopify-to-scale)).

## 3. Discovery and identity across clusters

The Multi-Cluster Services API (KEP-1645) exports a Service by creating a ServiceExport next to it; exports are opt-in, and an importing cluster gets a ServiceImport reachable at `<service>.<ns>.svc.clusterset.local`. A ClusterSet is "a group of clusters with a high degree of mutual trust and shared ownership", and within it same-named namespaces are one namespace with a single governing authority. The KEP does not prescribe an implementation and its API is `v1alpha1` ([KEP-1645](https://github.com/kubernetes/enhancements/blob/master/keps/sig-multicluster/1645-multi-cluster-services-api/README.md)). SIG-Multicluster defines namespace sameness as "Permissions and characteristics are consistent across clusters for a given namespace" ([namespace sameness](https://multicluster.sigs.k8s.io/concepts/namespace-sameness/)).

Cilium ClusterMesh needs a unique cluster name and numeric ID (1 to 255), allows 255 clusters by default or 511 with `maxConnectedClusters`, and requires non-overlapping pod CIDRs, node-to-node IP reachability and the same datapath mode in every cluster ([ClusterMesh setup](https://docs.cilium.io/en/stable/network/clustermesh/setup/index.html)).

Istio offers multi-primary (each cluster has its own control plane and its own configuration, duplicated by tooling) or primary-remote, on one network or several joined by gateways. Inside one mesh every service is shared by namespace sameness. Meshes with different trust domains must federate identity and trust bundles, and "Istio does not provide any tooling to exchange trust bundles across meshes" ([Istio deployment models](https://istio.io/latest/docs/ops/deployment/deployment-models/)).

SPIFFE federation is that exchange. Each SPIRE server governs one trust domain and serves its trust bundle at a bundle endpoint; operators exchange the first bundles out of band, later updates are fetched automatically, and a workload registered with `federatesWith` receives the foreign domain's bundle so it can verify callers from it over mTLS ([SPIFFE federation](https://spiffe.io/docs/latest/architecture/federation/readme/)).

### What an inter-estate contract needs at minimum (interpretation)

Read together, the sources separate two cases. Clusters under one owner can be a ClusterSet with namespace sameness. Estates with separate services and keys are not: they trust each other less than a ClusterSet assumes, so they federate, as Istio and SPIFFE do between trust domains. A minimal contract between estates would then carry: a stable, unique estate identity (shaped like KEP-2149's ID); a trust anchor per estate, exchanged once and rotated by fetch (SPIFFE bundles); an explicit export list, never an implicit merge by name (MCS's opt-in ServiceExport rather than sameness); names that cannot be mistaken for local ones (the `clusterset.local` precedent); and either non-overlapping addressing for a flat network (ClusterMesh) or gateways between networks (Istio multi-network).

## 4. More than a thousand Tenants in one cluster

### The two native models

Kubernetes names two ways to share a cluster: a namespace per tenant, or a virtual control plane per tenant. Namespace isolation is well supported and has "negligible resource cost", but does not cover cluster-scoped resources such as CRDs, StorageClasses and webhooks; a virtual control plane covers those at "somewhat higher resource usage" and harder sharing between tenants, and still leaves the data plane to isolate separately ([multi-tenancy](https://kubernetes.io/docs/concepts/security/multi-tenancy/)). The same page recommends a namespace per workload even when one tenant runs several, warns that a namespace per tenant makes per-workload policy hard and forces a single choice of grain, and suggests sandboxed containers when tenants can run untrusted code.

In the multi-customer (SaaS) case the tenants never touch the cluster, and "a 'tenant' is simply a group of users who share a single workload"; hybrids of per-customer workloads for sensitive data plus shared multi-tenant services are common (same source). AWS draws the same line: in a SaaS setting the application, not the tenant, talks to the Kubernetes API, and each tenant's access control is usually independent of Kubernetes RBAC ([EKS tenant isolation](https://docs.aws.amazon.com/eks/latest/best-practices/tenant-isolation.html)). It warns that by default any pod can enumerate every Service through CoreDNS, that quotas should force every tenant to set requests and limits, and that dedicating nodes per tenant becomes complicated and cost-prohibitive with many tenants (same source).

### Silo, pool and tiers

AWS's SaaS isolation paper names the application-level choice. A silo gives each tenant a whole stack: simple to enforce and small blast radius, but at a thousand tenants it "would likely begin to impact operational efficiency and agility" ([silo](https://docs.aws.amazon.com/whitepapers/latest/saas-tenant-isolation-strategies/silo-isolation.html)). A pool shares compute and storage keyed by tenant ID: efficient and operated as one, but isolation can no longer rest on network and IAM constructs, a noisy neighbour can hurt others, and an outage reaches every tenant ([pool](https://docs.aws.amazon.com/whitepapers/latest/saas-tenant-isolation-strategies/pool-isolation.html)). Tiers mix them: most tenants pooled, a few paying for a silo that runs the same version as the pool, "a clone of the pooled environment that happens to be supporting one tenant" ([tiers](https://docs.aws.amazon.com/whitepapers/latest/saas-tenant-isolation-strategies/tier-based-isolation.html)). AWS marks the paper as historical reference.

### Tools and their status

Capsule groups namespaces into a Tenant with per-tenant policy and quotas ([Capsule docs](https://projectcapsule.dev/docs/)); it is a CNCF Sandbox project, accepted 2022-12-13 ([CNCF](https://www.cncf.io/projects/capsule/)). vcluster gives each tenant its own API server running in a host namespace; its docs say shared worker nodes "aren't a security boundary for untrusted tenants" ([vcluster](https://www.vcluster.com/docs/vcluster/introduction/what-are-virtual-clusters)). The Hierarchical Namespace Controller was archived on 2025-04-17 and is read-only ([HNC](https://github.com/kubernetes-retired/hierarchical-namespaces)). The Kubernetes multi-tenancy page has dropped its links to third-party projects ([multi-tenancy](https://kubernetes.io/docs/concepts/security/multi-tenancy/)).

On the delivery side, Flux's multi-tenancy lockdown sets `--no-cross-namespace-refs`, `--no-remote-bases` and `--default-service-account`, so every Kustomization and HelmRelease reconciles as an account in its own namespace ([Flux multi-tenancy](https://fluxcd.io/flux/installation/configuration/multitenancy/), [impersonation](https://fluxcd.io/flux/components/kustomize/kustomizations/)). The estate already locks Flux down per Project ([record 58](../decisions/0058-flux-is-locked-down-per-project-and-delivery-dry-runs-as-an-identity-that-cannot-write.md)).

### The arithmetic for this estate

Against the 10,000-namespace threshold (section 1), the grain decides everything. A namespace per Tenant per environment is 3,000 namespaces at 1,000 Tenants: inside the threshold, with room for growth, but a third of it. A namespace per Tenant per Project per environment, at today's ten or so Projects ([record 1](../decisions/0001-one-maintainer-one-cluster-one-estate.md)), is about 30,000: three times over. A namespace per Project per environment, with Tenants as data inside pooled Applications, stays near 30 whatever the Tenant count. Each namespaced Flux object multiplies the same way, which is where Flux sharding would come in.

## 5. Implications for estate-kit (interpretation)

This section is my reading of the sources against the records, not a finding of any source. [Record 1](../decisions/0001-one-maintainer-one-cluster-one-estate.md) allows only seams that cost nothing now; each item below is meant to pass that test, and none adds a cluster axis.

1. **Treat (A) as cells, not as a ClusterSet.** Several estates, each with its own service, Render signing key, Writer Lease and Flux, are AWS cells and Flux standalone mode: separate blast radius, no hub to compromise. Nothing in the delivery path has to change for that; the signed registry tag ([record 9](../decisions/0009-the-live-render-is-a-signed-registry-tag-per-project-and-environment.md)) is already a pull seam each cluster's Flux verifies on its own. The one cost-free care is not to let anything assume a single estate shares the registry: keep the `render/` and `host/` package paths built in one place, not repeated as literals.
2. **Give the estate one stable name now, shaped like a cluster ID.** The Single-cluster fixture will refuse any cluster name but the estate's one. If that name is an RFC 1123 DNS subdomain under 128 characters, it can later serve as KEP-2149's `cluster.clusterset.k8s.io`, a ClusterMesh cluster name (at most 32 characters, so keep it that short), a SPIFFE trust domain and the qualifier in an inter-estate export, without renaming anything.
3. **Make Surfaces the export list, and keep them explicit.** CONTEXT.md already defines a Surface by name, port and providing Project and Application, and Link reads Surfaces only by declaration. That matches MCS's opt-in ServiceExport rather than namespace sameness, which assumes one authority over every same-named namespace. Keeping cross-Project references to declared Surfaces, never to bare Service names, keeps an inter-estate contract a matter of qualifying a Surface by estate later.
4. **Choose the Tenant grain before Tenants arrive: Tenant as data, Project as namespace.** For (B) at 1,000+ Tenants, the pool model with a namespace per Project per environment keeps namespaces, Flux objects and Prod tags proportional to Projects, not Tenants, and leaves the silo as a priced exception that runs the same render. The vocabulary already points this way: a Tenant is not an operator of the estate.
5. **Never let one Tenant's data or request span another's.** Shopify's "no action across pods" and AWS's partition key are what make a Tenant movable to another cell later. If every Application keys its state by Tenant and no request joins across Tenants, a later split by Tenant is a data move plus a routing table; if not, it is a rewrite. This costs a review rule now, not a model concept.
6. **Count environments into every limit.** Development, staging and production in one cluster multiply every count above by three and share one upgrade, one etcd and one blast radius. The `render/<project>:<environment>` tag already carries the environment; CONTEXT.md's Prod tag still says `prod` is the only one, so its definition is the term to widen first.
7. **Pick a non-default, estate-unique pod and service CIDR at the next rebuild.** ClusterMesh needs non-overlapping pod CIDRs, k3s's default caps a cluster at 255 nodes, and the flag must match on every server; choosing it at install costs nothing, while changing it later is likely a rebuild.
8. **Watch the datastore, not the node count.** At the estate's size the first k3s limit is likely etcd or kine object volume (2 GiB default, 8 GiB suggested ceiling) from per-Tenant objects and Events, not nodes. Keeping the Rollout log in Postgres ([record 23](../decisions/0023-a-rollout-is-an-append-only-event-log-on-the-shared-postgres.md)) and one ProjectControl per Project, not per Tenant, already avoids the obvious growth.
9. **Adopt no multi-cluster framework now.** MCS and ClusterProfile are `v1alpha1`, Flux is not among ClusterProfile's consumers, KubeFed and HNC are archived. If a second cluster comes, revisit at [record 1](../decisions/0001-one-maintainer-one-cluster-one-estate.md)'s horizon with ClusterProfile and SPIFFE federation as the first candidates.
